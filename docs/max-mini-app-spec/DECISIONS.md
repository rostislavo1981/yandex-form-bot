# 🧭 DECISIONS — журнал архитектурных решений (ADR)

Каждое решение — краткая запись с контекстом, вариантами, выбором и последствиями. Формат ADR (Architecture Decision Record) в облегчённом виде.

**Правила:**
- Если ты (агент) отклоняешься от того, что здесь написано, — сначала добавь новую запись с обоснованием.
- Не удалять старые записи. Если решение отменено — добавить новую с пометкой «отменяет ADR-N».
- Свежие — снизу.

---

## ADR-001. PostgreSQL, не SQLite

**Дата:** пре-Phase 0
**Статус:** принято
**Контекст:** нужен реестр отчётов с нормализованной моделью (объекты, этапы, справочники, строки техники и работ).
**Варианты:**
1. SQLite — просто, файл рядом с приложением.
2. PostgreSQL — сложнее в деплое, но полноценные UNIQUE/CHECK/FK, конкурентный доступ, JSONB на будущее.
**Выбор:** PostgreSQL 16.
**Обоснование:** нужны конкурентный доступ (bot + api), нормализация, UNIQUE constraints (`title_code`, `(object_id, name)`), возможность горизонтального расширения на пост-MVP.
**Последствия:** обязателен Docker/managed БД в деплое; тесты используют реальную БД.

## ADR-002. Bot и Backend — разные процессы

**Дата:** пре-Phase 0
**Статус:** принято
**Контекст:** бот должен слушать long polling, backend — обрабатывать HTTP-запросы Mini App.
**Варианты:**
1. Один процесс: FastAPI + фоновая задача poller через `lifespan`.
2. Два процесса в одном codebase: `python -m app.main` для API, `python -m app.bot` для polling.
**Выбор:** два процесса.
**Обоснование:** возможность перезапускать бот, не роняя API; проще масштабировать и логировать; проще писать e2e-тесты API без запуска бота.
**Последствия:** нужен внутренний канал bot↔backend (пока — HTTP, потом можно очередь).

## ADR-003. HMAC-верификация initData по Telegram-схеме

**Дата:** пре-Phase 0
**Статус:** принято, **[непроверено]**
**Контекст:** документация MAX Mini App API на момент написания спеки не изучена детально.
**Гипотеза:** MAX использует ту же схему, что Telegram WebApp: `HMAC_SHA256(SHA256(bot_token), data_check_string)`.
**Выбор:** реализуем по Telegram-схеме, помечаем `[непроверено]` в коде.
**План отмены:** если официальная документация MAX опишет другую схему — заменить содержимое `webapp_auth.py` (интерфейс `verify_init_data(str, str) -> dict` сохранить).
**Последствия:** frontend и middleware завязаны на строку `X-Auth-InitData`. Если формат имени заголовка/поля отличается — переименовать в одной точке.

## ADR-004. Frontend без UI-фреймворка

**Дата:** пре-Phase 0
**Статус:** принято
**Контекст:** MVP-форма с ~20 полями. UI-либа (MUI, Chakra) добавит сотни KB и время на изучение.
**Выбор:** React + Vite + TS + обычный CSS. Никаких UI-либ.
**Обоснование:** быстрый старт, малый bundle (важно для мобильного webview), полный контроль над мобильной вёрсткой.
**Последствия:** дизайн простой; если позже понадобится компонентная библиотека — вводится точечно.

## ADR-005. Long polling, не webhook

**Дата:** пре-Phase 0
**Статус:** принято
**Контекст:** старт быстрый, VPS с HTTPS для webhook на первом этапе может отсутствовать.
**Выбор:** long polling через `getUpdates`.
**Обоснование:** работает без внешнего HTTPS-эндпоинта; проще отладка (можно запускать бота локально).
**Переход на webhook:** запланирован как пост-MVP улучшение (Phase 7+).
**Последствия:** один инстанс бота (иначе гонки за offset). При росте нагрузки — переход на webhook.

## ADR-006. Без Alembic в MVP

**Дата:** пре-Phase 0
**Статус:** принято
**Контекст:** миграции пока не нужны — схема стабильна.
**Выбор:** `Base.metadata.create_all()` на старте.
**Отмена:** ввести Alembic в Phase 7 (или раньше, если понадобится менять модель на проде).
**Последствия:** любое изменение модели в первые недели — через `docker compose down -v` (сброс БД). Для прода — до Alembic БД не апгрейдить.

## ADR-007. Русские тексты в API-ошибках

**Дата:** пре-Phase 0
**Статус:** принято
**Контекст:** API вызывается только Mini App'ом, конечный пользователь — русскоязычный прораб.
**Выбор:** `{"detail": "Этап не принадлежит объекту"}` — сразу по-русски.
**Обоснование:** frontend не переводит, просто показывает; экономия времени.
**Последствия:** если появятся другие клиенты — вводить локализацию (тогда i18n-ключи).

```md

**Дата:** YYYY-MM-DD
**Статус:** принято | отменено ADR-XXX | предложено
**Контекст:** почему возник вопрос
**Варианты:** какие рассматривали
**Выбор:** что выбрали
**Обоснование:** почему
**Последствия:** что это меняет для остальных частей
```
