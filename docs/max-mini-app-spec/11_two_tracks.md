# 11. Два трека развития: Bot-first и MiniApp-first

Есть два способа собрать один и тот же продукт. Оба заканчиваются одинаково — прораб сдаёт отчёт, данные лежат в PostgreSQL, руководитель качает Excel. Разница — в **порядке фаз** и в том, **что готово раньше**.

## Общее ядро (обязательно для обоих треков)

Эти фазы одинаковые и делаются всегда, независимо от выбранного трека:

- **Phase 0 — Bootstrap** (1 день)
- **Phase 1 — Модель данных и БД** (1 день)
- **Phase 2 — API отчётов** (2 дня)

**Итого ядро: ~4 дня.** После него в БД можно писать отчёты через curl.

## Трек A — Bot-first (рекомендуется)

**Идея:** сначала выпускаем бота-опросника. Прораб уже сдаёт отчёты. Mini App добавляем потом как второй канал.

**Фазы после ядра:**
- **Phase A1 — MaxClient + стейт-машина диалога** (2 дня)
- **Phase A2 — `/summary`, `/export` команды бота** (1 день)
- **Phase A3 — Опционально: Mini App поверх готового ядра** (7–8 дней)

**До первого прод-релиза:** ~7 дней (Phase 0 + 1 + 2 + A1 + A2).
**MVP полностью готов.** Mini App — как второй этап, если нужен.

**Что теряется на старте:**
- Нет визуальной сводной с карточками (только `/summary` → Excel).
- Правка отчёта на лету неудобна (надо идти назад по шагам).
- Ввод длинного списка техники утомителен.

**Что выигрывается:**
- Нет HTTPS, нет доменов, нет Caddy, нет CORS.
- Нет HMAC-верификации initData (риск с `[непроверено]` в ADR-003 снят).
- Нет React/Vite/TypeScript — только Python.
- Отладка через логи бота, не через chrome-devtools внутри MAX.
- Прораб получает работающий инструмент **на неделю раньше**.

## Трек B — MiniApp-first

**Идея:** сначала полноценная форма в webview, потом (или никогда) команды бота-опросника.

**Фазы после ядра:**
- **Phase B1 — Frontend MVP** (3 дня)
- **Phase B2 — Сводная и Excel в UI** (1 день)
- **Phase B3 — Bot + HMAC** (3 дня)
- **Phase B4 — Прод-деплой с HTTPS** (1 день)

**До первого прод-релиза:** ~12 дней (Phase 0 + 1 + 2 + B1 + B2 + B3 + B4).

**Что теряется:**
- Первый рабочий отчёт от прораба сдвигается на неделю дальше.
- Риск в Phase B3: если HMAC MAX окажется не как в Telegram — переделка.
- Обязательный VPS с HTTPS с самого старта.

**Что выигрывается:**
- Сразу отличный UX для повседневного ввода: одна страница, всё видно, добавлять строки быстро.
- Визуальная сводная с карточками.

## Сравнение

| Критерий | Трек A (Bot-first) | Трек B (MiniApp-first) |
|---|---|---|
| **Дней до первого прод-релиза** | ~7 | ~12 |
| **Стек** | только Python | Python + React/TS |
| **Инфра для MVP** | VPS без HTTPS | VPS + домен + HTTPS |
| **Регистрация Mini App в BotFather** | не нужна | обязательна |
| **HMAC-верификация** | не нужна | обязательна (с `[непроверено]`) |
| **Работа на плохом инете** | лучше | хуже |
| **Скорость ввода 5 строк техники** | ~1 мин (много кликов) | ~20 сек (одна форма) |
| **Правка на лету** | плохо | хорошо |
| **Аудит-след в чате** | весь диалог виден | только «✅ Отчёт №42» |
| **Порог входа для прораба** | «как переписка» | «понять форму» |

## Рекомендация

**Трек A.** Аргументы:
1. Быстрее до реальной пользы (7 vs 12 дней).
2. Меньше движущихся частей, ниже риск застрять.
3. Backend и модель данных **общие** — любой трек не блокирует второй. Даже начав с A, можно спокойно добавить Mini App позже (это станет Phase A3).
4. Риск `[непроверено]` про MAX HMAC снят: если что-то не так с initData, вы уже в проде с ботом-опросником.
5. Прорабы, привыкшие к WhatsApp/Telegram, чаще предпочитают короткие сообщения-диалоги, а не большую форму.

Трек B оправдан только если:
- HTTPS-домен уже настроен.
- Есть готовность потратить лишнюю неделю на UX ради 20-секундного ввода вместо минутного.
- Известно, что прорабы будут сдавать по 3–5 отчётов в день (тогда быстрая форма экономит время).
